# ADR 0044: QR presentation profiles — demo pages on the existing QR registry

- **Status:** Proposed — owner request 2026-11-05 (presentation package: two bottles, a liquid
  soap 330 ml and a Mixt gel 330 ml for body and hair); model and publication scope for review
  before any database implementation. Details in doc 046.
- **Date:** 2026-11-05
- **Context:**
  - The public bottle passport (`GET /api/public/bottles/:token`, page `/q/<token>`) returns only
    `bottleCode` and `reuseCycles` (doc 011, `publicBottlePassportSchema`).
  - Tokens are 128 random bits, 22 base64url characters (ADR 0014). They are registered once in
    `qr_identities` (kinds `BOTTLE`, `CRATE`, `WORKSTATION`) by database triggers, so a token is
    unique across kinds and never reused.
  - The production edge (doc 037, ADR 0035) publishes only `GET`/`HEAD /<token>` → `web` `/q/<token>`.
    The owner verified it read-only on 2026-11-05: valid HTTPS, an unknown token answers 404,
    `/login` answers 404. PROD runs `b060802`.
  - The owner wants two presentation QR codes that open a clear mobile page. No QR for them is
    printed yet (owner 2026-11-05), so their identities are created new.
  - A presentation must never create stock movements, bottles or reuse cycles.

## Decision

1. **A presentation is its own QR kind, not a bottle.**
   - A new value `PRESENTATION` of `QrIdentityKind` and one table `qr_presentations`.
   - The table holds the identity and which fixed profile it shows; no content.
   - A presentation token can never resolve to a bottle, and a bottle's token never to a
     presentation (the registry's `(token, kind)` FK, as crates and workstations).
2. **The content is code, versioned in Git, not a CMS.**
   - Two profiles, keys `HAND_SOAP_330` and `MIXT_GEL_330`. Their texts live in the repository
     (like the contract template, ADR 0043) and change only by a PR.
   - Only documented content: the product name, "330 ml", and general use (hands; body and hair).
   - No INCI, composition, origin, ecological or CO2e figure, no reuse count, no claim of a real
     cycle (doc 011).
3. **Identities are created per environment, explicitly, once.**
   - An ADMIN creates a profile's QR in the internal app by an explicit action. The token is
     generated by the application (`generatePublicToken`), never by a migration, so DEV and PROD
     never share a token.
   - One live identity per profile (unique index). The token is immutable (DB trigger, as
     `qr_identities`). A retirement is a new state, never a deletion, and is not part of this
     delivery.
4. **Public DTO: a separate, closed schema.**
   - `GET /api/public/presentations/:token` → `{ kind: 'PRESENTATION', profile, demo: true }`,
     strict, no internal ID, creator or time.
   - The same rate limit and cache headers as the bottle passport.
   - The page shows a permanent "DEMO" marking. It never shows a bottle code or a reuse count.
5. **No topology change.**
   - The page `/q/<token>` adds presentations to its existing lookup (bottle → crate → workstation
     → presentation).
   - The PROD edge already forwards `/<token>`: nothing in Caddy, DNS or the host guard changes.
     On DEV the page stays tailnet-only (ADR 0026).
   - The QR encodes only `PUBLIC_QR_BASE_URL/<token>` (ADR 0014). A DEV QR carries
     `DEV - NOT FOR PRODUCTION`.
6. **Management in Správa systému.**
   - A new permission `qr:presentations_manage`, granted to ADMIN in the same migration.
   - The page lists the two profiles. For each one it offers creating the QR (once), opening the
     public page, and previewing and downloading the QR as SVG.
   - Creating is audited.

## Consequences

- Real bottles keep the existing whitelist and the verified history; nothing in their passport
  changes.
- No new runtime, container, vendor, secret or public path. Deployment is the ordinary core
  release.
- A PROD presentation QR exists only after an ADMIN creates it on PROD, after the owner's approved
  release.
